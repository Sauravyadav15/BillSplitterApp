# 0006. Document AI "Document OCR" as a third selectable OCR provider

Status: Accepted
Date: 2026-08-12

## Context

[ADR 0005](0005-google-vision-ocr-option.md) added Google Cloud Vision as a hosted-API alternative to self-hosted PaddleOCR. Separately, Google Cloud Document AI was evaluated as another option, starting with its **Expense Parser** processor — a specialized model that extracts structured entities (merchant, total, and per-line `line_item/description` + `line_item/amount`) directly, rather than plain text.

Tested against a real receipt (a Food Basics grocery receipt, the same style as `backend/tests/fixtures/foodbasicsbill.jpeg`), Expense Parser detected item names consistently but linked prices to line items inconsistently — several item prices (e.g. produce and bakery lines) weren't picked up as `line_item/amount` entities at all, while others in the same receipt were. That's a property of the trained entity-linking model, not a configuration option; fixing it for real would require uptraining Document AI's **Custom Extractor** with a hand-labeled set of receipts, which is disproportionate effort for this project's scale.

Document AI's **Document OCR** processor (a general-purpose plain-text extractor, no entity linking) was tried next and extracted all text/prices accurately and consistently.

## Decision

Add `backend/utils/receiptOcrDocumentAI.js` as a third OCR backend, selected via `OCR_PROVIDER=documentai`, calling a Document AI **Document OCR** processor's `processDocument` API and returning `document.text` (already in reading order, like the Vision path) — not Expense Parser, and not any other Document AI processor type.

Unlike the Vision path, this text is **not** fed through `receiptParser.js`. It has its own dedicated parser, `backend/utils/receiptParserDocumentAI.js`, selected alongside the OCR backend via `backend/utils/parserProvider.js` (mirrors `ocrProvider.js`'s switch). See "Why a dedicated parser" below for why sharing `receiptParser.js` wasn't viable.

Configuration mirrors the Vision provider's pattern: `DOCAI_PROJECT_ID`, `DOCAI_PROCESSOR_ID`, `DOCAI_LOCATION` (default `us`) identify the processor, and `GOOGLE_DOCAI_KEY_FILE` (or the standard `GOOGLE_APPLICATION_CREDENTIALS`) provides credentials. `utils/ocrProvider.js` gained a third `case` for it; `paddle` (self-hosted) remains the default, so this is a non-breaking addition.

## Consequences

- Document AI processors are provisioned per-project in the Cloud Console (not just an enabled API), so switching to `documentai` requires the processor to already exist — the specific processor used in testing was created as `smartbillsplit2` (Document OCR, region `us`) in the project's Document AI console.
- Same tradeoff as ADR 0005 applies here too: no local Python/model footprint, small per-page API cost, and the receipt photo leaves the server to Google's API.
- Expense Parser (and Document AI's other specialized/custom processor types) were evaluated and explicitly rejected for this use case, not merely unused — worth remembering before reaching for them again on a similar problem.

### Why a dedicated parser (`receiptParserDocumentAI.js`), not `receiptParser.js`

`document.text`'s reading order reliably keeps an item's name and price adjacent *within* the dense item-list section, but real receipts (tested against all of `backend/tests/fixtures/`, spanning four different stores) exposed several ways Document AI's line-splitting behavior actively corrupts `receiptParser.js`'s "use the previous line as the item name" fallback, which assumes name and price are almost always on the same line:

- **A per-item code printed on its own line** (e.g. `MRJ`, `HMRJ` on a Loblaws-family receipt) between an item's name line and its price line was clobbering the real pending name (`OREO MINT` → `MRJ`) - the same failure mode as the `FROZEN FOOD` → `FOOD` bug below, just recurring on almost every row instead of once.
- **A promo/adjustment annotation** (`ARCP: 50.00% ($6.49)`, or a bulk-price blurb like `$2.47 Int 4, $3.77 ea`) reads as a second priced line, or has just enough incidental letters to pass as a real name, and became a duplicate fake item or replaced the real name outright - while the real discount/total that followed was silently dropped.
- **A bare per-unit rate on its own line** (`2 @ $2.69`, `0.500 kg $8.80/kg`, `$11.00/kg`) was taken as the item's final price, when the real line total is a separate, later orphaned line - e.g. a weighed produce item's Gross/Tare/Net weight breakdown spans three lines before the per-kg rate and, finally, the real total.
- **A charge label with no price of its own** (e.g. `ECOLOGY FEE`, its value arriving as part of a later cluster of unrelated values) was read as a normal name candidate and clobbered the real pending item name, cascading into three consecutive items getting each other's prices.
- **The SUBTOTAL/TOTAL section's labels land far from their values** (see below) - and on `metrobill.jpeg` this produced a fake item, `{name: "AIR MILES", price: 56.15}`, where 56.15 was actually the receipt's real total. That's a real, silently-wrong dollar amount, not just a missing feature.

`receiptParserDocumentAI.js` originally fixed all but the last of these (subtotal/total, discussed next) with a small state machine built around two queues (`pendingQueue` for names/charge-labels waiting on a price, `tentativeQueue` for items whose price could still be refined by a later rate/promo line). That design was replaced with a simpler single-pass state machine, built around an explicit line classification (ITEM NAME / ITEM PRICE / ITEM NOTE / DISCARD / FOOTER) rather than queues: Document AI reliably keeps a name and its price adjacent (the very next non-noise, non-code line), so only one pending name and one pending "fragment" (a bare weight or count line waiting for its rate/multi-buy value on the next line, e.g. `"0.480 kg"` then `"$3.28/kg"`, joined into one `"0.480 kg @ $3.28/kg"` unit note) ever need to be held at once - the two-queue design was solving for a "several names in a row before any price shows up" case that direct comparison against the old parser (on the same fixtures, see below) showed wasn't actually happening in practice, while its same-type-collapse rule for `pendingQueue` was actively harmful: a single stray OCR character (e.g. a bare `"H"`) landing between a real item's name and its price would silently overwrite the real name via collapsing, then fail the letter-count check and vanish the item entirely - confirmed on a real fixture (`bill2.jpeg`), where it silently dropped 5 real items this way. The new design checks letter-count *before* a candidate is ever allowed to become a pending name, so a stray fragment like `"H"` or a bare barcode line is dropped immediately without disturbing whatever real name is already pending.

Still carried over unchanged in the new design:
- A `looksLikeCodeFragment` check (short, all-caps, **fewer than 2 vowels**) for per-item codes like `MRJ`/`GPMRJ`/`RQ` - length alone isn't safe, since a real short single-word item name standalone on its own line (`BANANA`, `KALE`, both seen in testing) has the same 2-6-letter all-caps shape and was being silently discarded by a length-only version.
- A `seenDepartmentHeader` gate: nothing before the first recognized department header (store name, logo tagline, address, loyalty blurb - too varied to noise-filter by keyword) is ever treated as a candidate name. This gate is pre-scanned rather than unconditional: some receipt formats (e.g. a Loblaws/Superstore-style bill, confirmed on a real fixture) print no department header anywhere at all, which left the gate permanently closed and silently dropped the entire receipt - items and charges alike - even though OCR text extraction was fine. `parseReceiptLines` checks up front whether the receipt contains a department header anywhere in its text at all; if it does, the gate behaves as before, and if it structurally never could (no such line exists), parsing starts from the first line instead.
- An `'arcp'` noise keyword, and a `CODE_FRAGMENT`/`WEIGHT_DETAIL_LINE` skip list for informational lines that are never a name or a price.
- A stop condition once `TOTAL` is seen (checked unconditionally, not gated behind having found `SUBTOTAL` first, so a garbled/missed `SUBTOTAL` label doesn't leave the payment-method section to be misread as more items) - what stops the `"AIR MILES" → 56.15` class of bug.

One accepted tradeoff of the simpler design: the old `tentativeQueue` would keep refining an item's price against *any* later plain orphaned value it found, even past the `SUBTOTAL`/`TOTAL` labels - which happened to recover the correct total on one fixture (`foodbasicsbill.jpeg`) where a 2-unit item's real line total (`5.38`) was printed, oddly, after `TOTAL` rather than next to its `"2@ $2.69"` rate line. The new design treats `TOTAL` as an unconditional stop and never revisits an item's price past it, so that one item now reports its per-unit rate (`2.69`) instead of the correct line total (`5.38`) on that specific receipt. This is a deliberate consequence of the explicit-rules approach this parser follows (an item's price, once set, is final - not something to keep recalculating against whatever number turns up arbitrarily later), not an oversight.

**Two further accuracy fixes**, found by checking the rewrite above against 8 more real receipts and comparing item-by-item against what the OCR text actually says (not just item counts):

- **A pending name now always claims the very next price-bearing line, no matter what else is on it.** Previously, if that line's own leading text happened to have enough letters to look like a plausible name (e.g. a garbled per-item code fused onto its price, `"MRJbnpr 5.50"` - "MRJ" plus stray OCR characters), it was read as a brand-new combined name+price item instead of resolving the real pending name - `"PC DECADENT DARK"` was silently replaced by `"MRJbnpr"` this way on a real fixture (`nofrillsBill.webp`). The combined-name-on-one-line path (still needed for the cases where Document AI genuinely does keep name and price together) is now only considered when no name is already pending.
- **A rate/multi-buy line no longer finalizes an item's price outright when a separate real total follows it.** A price opened from a rate-signal line (e.g. `"$11.00/kg"`, `"2 @ $2.00"` - some non-price text before the price, or a `/kg`/`/lb`/`/ea` suffix after it) is held provisional: the rate line is still recorded as the item's unit note, but the *next* plain value refines the price to the real total instead of a second item being started. Without this, an item whose OCR text puts a per-unit rate line before its real line total (e.g. `"GRP GRN SDLS"` on `loblawsbill.webp`: `"$11.00/kg"` then, on its own line, `"11.49"`) was undercharged at the rate value (`11.00`) instead of the real total (`11.49`) - a silent, real dollar-amount error, not a cosmetic one. Confirmed correcting the same class of bug on several other items across `grocerybill2.jpg`, `metrobill.jpeg`, `nofrillsBill.webp`, and `longfoodbasicsbill.webp` (e.g. `"PEP ORANGE SWT"` was landing at its per-kg rate `10.98` instead of its real `8.51` line total). A further rate-signal line keeps the price provisional and adds another note rather than refining early; only a plain value closes it.

One fix found during the original two-queue work is general enough to belong in the shared `receiptParser.js` too, and was ported: it only stripped `frozen` from a category header, so a receipt with a compound "FROZEN FOOD" section header left "FOOD" behind as a residual fragment that clobbered a real item's name; `'frozen food'` was added ahead of `'frozen'` in both files. `receiptParser.js` also separately gained its own `BARE_EACH_MARKER` fix (an "EA" each-unit confirmation line, e.g. `3EA @ $0.99/EA`, was being read as a bogus item named "EA" on a Trader Joe's receipt) - a real bug in the shared PaddleOCR/Vision path, unrelated to Document AI's line-splitting.

**Known remaining gap**: on one receipt with an unusually severe promo-line format (`$6.97 lot 4, $9.99 ea` collapsing into OCR garbage like `186.97 ев`), an item's price got closed by a corrupted intermediate number instead of the real final total, landing on `3.48` instead of the correct `6.97`. This is a genuine unresolved edge case, not a design gap covered above - the underlying rate-signal detection can't recognize a quantity marker that OCR has already destroyed. Not chased further given diminishing returns relative to the fixes already made; revisit if it recurs on other receipts from the same store. Separately, an OCR misread that drops a savings label's leading letters (e.g. `"Saving 1.00"` read as `"ing 1.00"`) no longer matches the `'saving'` noise keyword and is read as a bogus item named `"ing"` - a pre-existing issue confirmed present in both the old and new parser on the same fixture (`bill2.jpeg`), not something introduced by this rewrite.

### Subtotal/total extraction: partially fixed, rest deliberately left as a known limitation

Document AI's reading order separates a label from its value across two different receipt footer layouts, and only one of them is safe to bridge:

- **Adjacent, no gap** (e.g. `SUBTOTAL` then `113.65` as the very next line, nothing between them) - `extractLabeledAmount` now checks this case: if a label line has no price of its own, and the *very next* line is nothing but a standalone price, use it. This is safe specifically because it only fires when there's a single unambiguous candidate immediately next to the label - it can't misattribute a value from elsewhere in the footer the way the rejected heuristic below could. Verified against all four test receipts: correctly recovers subtotal on a Loblaws receipt and both subtotal *and* total on a Real Canadian Superstore receipt, while still correctly returning `null` (not a wrong guess) on the two receipts where the label and value truly aren't adjacent.
- **Separated by other lines, or clustered together disconnected from their labels** (e.g. `metrobill.jpeg`'s "Your savings today" promotional block sitting between the labels and their real values) - still returns `null` when nothing else can confirm a value (see the arithmetic fallback below for the cases where something can). A positional heuristic ("the first orphaned footer value is the subtotal, the last is the total") was prototyped for this case and rejected: it happened to produce the right answer on 2 of 3 test receipts, but on `metrobill.jpeg` it would have confidently returned a plausible-looking *wrong* number. A wrong subtotal is worse than a missing one in a bill-splitting app, so this was not shipped.

**Update - arithmetic-verified fallback**: `extractTotal` and `extractSubtotal` each gained a second-chance path for exactly the "separated" case above, but built on the same principle that sank the rejected positional heuristic: never accept a value that isn't independently checkable. If the label-adjacent extraction is missing or doesn't reconcile with the other side of the bill (`subtotal + sum(charges)` vs. `total`, within a couple of cents), the unreconciled value is treated as unreliable and discarded outright - not kept as a fallback-of-last-resort - and only replaced if a genuinely verified candidate turns up:
- `extractTotal` searches the raw text for a value next to a payment-section marker (`"DEBIT"`, `"TENDER"`, `"CAD$"`, a card network name) or a bare amount near the end of the receipt, and accepts one only if it makes the arithmetic check out. This is what recovers `loblawsbill.webp`'s total: Document AI reads `"TOTAL"` as `"ΤΩΤΑΙ"` (the exact garbled-label case `extractLabeledAmount`'s comment already calls out as unrecoverable on its own), but `"107.75"` appears as a bare value two lines later and exactly matches `subtotal (107.07) + charges (0.68)`, so it's accepted.
- `extractSubtotal` has no equivalent payment-marker pattern to search for (a subtotal isn't printed next to "TENDER"), so it instead searches from the `SUBTOTAL` label's own position onward (when the label exists at all, even without an adjacent value) for a candidate matching `total - charges`.
- Both had to be hardened against a real false-positive found in testing: naively computing `total - charges` (for subtotal) or including the subtotal's own printed value in a broad "any bare number near the end" search (for total) can trivially "verify" itself when charges happen to be miscounted as zero, since `subtotal + 0 = subtotal` and `total - 0 = total` are true by construction, not confirmation of anything. Confirmed on two fixtures: `bill2.jpeg`'s garbled/undetected tax line left `chargesTotal` at `0`, which would have produced a wrong subtotal (`82.96`, silently equal to the total) without this guard; `grocerybill1.jpeg`'s subtotal briefly self-matched as a "total candidate" the same way. Fixed by excluding the subtotal's own label-and-value lines from the search rather than trusting the arithmetic blindly.
- The tradeoff this makes explicit: a label-adjacent value that doesn't reconcile is now discarded even when it might actually have been correct (e.g. `grocerybill1.jpeg`'s and `grocerybill2.jpg`'s totals, both real values that just don't reconcile because a garbled/non-adjacent tax line elsewhere on the same receipts couldn't be captured as a charge) - the reconciliation check can't distinguish "this total is wrong" from "this total is right but our charge detection is incomplete." Between silently keeping a total that might be stale relative to the charges this file *did* find, and returning `null`, this file consistently chooses the latter.

Tax line extraction (GST/PST-style charges) has an additional problem beyond adjacency on top of this: on the Real Canadian Superstore receipt, the labels themselves arrived OCR-garbled beyond recognition (`"G=GST 5%"` read as `"68ST 5%"`), so even a perfect adjacency fix can't match `CHARGE_LABEL_PATTERN` against them. Still not addressed for that specific garbling case - a different problem (OCR accuracy on this specific glyph) than the layout issue below fixes.

**Update**: `parseReceiptLines` now captures tax/fee charges positionally, between the `SUBTOTAL` and `TOTAL` lines, rather than relying solely on `CHARGE_LABEL_PATTERN` matching during the main item pass (which required the label and its price to be combined on one line, and silently missed a clean, unmangled label like `"TOTAL TAX"` sitting on its own line with the value on the very next line - confirmed on `grocerybill3.webp`, which previously returned zero charges despite printing a perfectly readable `"TOTAL TAX" / "$0.19"` pair, simply because the old per-line pass stopped resolving `pendingQueue` once past the `SUBTOTAL` boundary). The fix mirrors `extractLabeledAmount`'s adjacency rule rather than reintroducing the rejected positional heuristic: within the `SUBTOTAL`-to-`TOTAL` window, any line matching `CHARGE_LABEL_PATTERN` (same-line with its price, or immediately followed by a standalone price line) is captured; anything else in that window that isn't a recognized charge label is simply ignored, not guessed at. This still doesn't recover the `"68ST 5%"`-style garbled-label case above - the label has to be recognizable text - but does now correctly recover a clean, un-garbled label whose value just isn't on the same line, and generalizes past tax specifically to any charge label already covered by `CHARGE_LABEL_PATTERN` (fees, surcharges, HST/PST/GST).

Reconstructing lines from Document AI's own per-line bounding boxes (the same y-position-grouping approach `ocrLineBuilder.js` uses for PaddleOCR - Document AI's `page.lines[]` does expose pixel `boundingPoly.vertices` per line) was also prototyped and would likely fix the non-adjacent case correctly, since it's a structural fix rather than a guess, but wasn't pursued: it requires `receiptOcrDocumentAI.js` to expose per-line box data (breaking the plain-text-only contract the other two providers share) and reusing `ocrLineBuilder.js`'s `LINE_GAP_FACTOR` threshold as-is caused *new* regressions elsewhere (two tightly-spaced rows on `foodbasicsbill.jpeg` merged into one garbled line) since that threshold was tuned against PaddleOCR's box-height reporting, not Document AI's. Revisit if this becomes a priority - it needs its own tuning pass, not a blind reuse.
