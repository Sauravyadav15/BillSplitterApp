# 0007. Token-coordinate-based parsing for Document AI, with arithmetic-validated fallback

Status: Accepted
Date: 2026-08-16

## Context

ADR 0006's `receiptParserDocumentAI.js` parses Document AI's `document.text` - a single flat reading-order string - by splitting on newlines and classifying each line. Nearly every real bug fixed in that file since (documented across ADR 0006 and several `CHANGELOG.md` entries: a per-item code line clobbering a pending name, a rate line finalizing an item at the wrong price, a receipt's own total getting misread as a fake item, a tax line's label landing lines away from its value) traces back to the same root cause: Document AI's own text-linearization algorithm doesn't always agree with the receipt's actual physical layout. A name and its price that are printed side-by-side on one visual row can come out as two separate "lines" in `document.text`, and lines that are physically far apart can end up adjacent.

Document AI's response carries more than just linearized text, though: `document.pages[].tokens[]` gives every word's own pixel-position bounding box (`token.layout.boundingPoly.normalizedVertices`) and a byte-range slice into `document.text` for its content. That's enough to reconstruct "which words are on the same physical row, in what left-to-right order" directly from geometry, instead of trusting Document AI's own linearization - addressing the root cause instead of continuing to patch symptoms of it with more text heuristics.

## Decision

`receiptOcrDocumentAI.js` gained `extractDocumentFromImage(imagePath)`, returning the full Document AI `Document` object (text + per-page tokens/geometry), alongside the existing `extractTextFromImage` (now a thin wrapper over it, so both entry points cost exactly one API call). Neither PaddleOCR nor Google Vision expose word-level geometry the same way, so this is documentai-specific, not a shared contract.

`receiptParserDocumentAI.js`'s existing line classifier (the state machine described in ADR 0006) was extracted into an internal `classifyLines(lines)` taking an already-split array of lines, so it can run unchanged against lines built two different ways:

- `parseReceiptLines(rawText)` and friends (**kept working exactly as before**, still exported) - `document.text` split on newlines.
- `parseReceiptFromDocument(document)` (**new**) - lines geometrically reconstructed from token positions:
  1. Correct Document AI's coarse `orientation` (90-degree steps only), then estimate and correct finer tilt as the *median* angle of each token's top edge, up to 15 degrees - median rather than mean so a handful of noisy token boxes (always present on a real photo) can't skew the estimate.
  2. Cluster tokens into rows by vertical-center proximity (tolerance = a multiple of the page's own median token height, not a fixed pixel count, so it scales with resolution and font size), sort each row left-to-right, and join into one text line.
  3. Feed those lines through the *same* `classifyLines` used for the text path - the geometry's job is producing correctly-grouped input, not reimplementing name/price/charge/note classification a second time.

The result is only ever trusted if it's arithmetically self-consistent: item prices should sum to the subtotal, and subtotal + charges should sum to the total (both within a couple of cents - reusing the arithmetic-verified `extractSubtotal`/`extractTotal` fallback already in this file). If the coordinate-based result doesn't reconcile, `parseReceiptFromDocument` returns the text-based result instead (flagged `needsReview: true` unless *that* happens to reconcile). It does **not** rank two non-reconciling results against each other and pick the "closer" one - see Consequences for why that was tried and reverted.

`billController.js`'s `parseReceipt` handler feature-detects `ocrProvider.extractDocumentFromImage` / `parserProvider.parseReceiptFromDocument` rather than checking `OCR_PROVIDER` directly, so paddle/google keep working through the unchanged text-only path with zero behavior change, and the response gained a `needs_review` boolean (`false` unless the coordinate path ran and neither side could verify itself).

## Consequences

- Verified against all 14 fixtures via live Document AI calls (not just unit-tested against captured text): the coordinate path fully reconciles and is used on 2 of 14 - both genuine, previously-unreachable recoveries. `bill1.jpeg` went from 0 items (the text path found nothing usable) to 1 correctly-priced item. `grocerybill1.jpeg` recovered a `STATE TAX 1` charge and its real total that the text path could never find, because the label and value are printed on the *same physical row* (Document AI's own text splits them across separate, non-adjacent lines with no way to know they belonged together). On the other 12, the coordinate result didn't reconcile and the proven text-based result was used instead, unchanged from before this ADR.
- A real tradeoff surfaced on `grocerybill1.jpeg` itself while tuning the row-clustering tolerance: a tighter tolerance (0.6× median token height) occasionally splits a multi-word item name across two rows when the page's median height is dominated by smaller fine-print text elsewhere on the receipt - confirmed stranding "-MUSHROOMS" in a different row than the rest of its own name and price. Widening the tolerance to fix that (0.75×) was tried and reverted: it started pulling a stray token in from the *next* row instead, corrupting the same item a different way, and broke the exact row separation that let the STATE TAX charge above be recovered at all on the same fixture. Kept at 0.6 - an occasional wrong item name is recoverable (this endpoint is preview-only; the frontend already expects the user to review and edit scanned items before a bill is created), losing a charge-capture that has no other path to succeed is not. This is a known, accepted gap, not an oversight - revisit if it recurs often enough in practice to justify a more locally-adaptive tolerance (e.g. based on each row's own token heights rather than one page-wide median) rather than a single global multiplier.
- The cascade deliberately does not compare two non-reconciling reconciliation errors and prefer the smaller one, even though that was the first design tried. Two real fixtures broke it: on `loblawsbill.webp`, a badly mis-clustered coordinate result (multiple items merged/duplicated, off by over $100) still scored a *smaller* arithmetic error than the text result's legitimate, unrelated-to-parsing-quality gap (~$8.50, from per-item promotional discounts that are intentionally discarded as noise per `classifyLines`' DISCARD rules - see ADR 0006). On `foodbasicsbill.jpeg`, the coordinate path dropped half the real items (6 of 12) but still "won," because the text path had no subtotal to check against at all, and "nothing checked" isn't a fair comparison against "checked and imperfect." The coordinate path is only ever used when independently verified - never as a preferred-but-unverified guess over the text path.
- The 90-degree orientation correction (`PAGE_RIGHT`/`PAGE_DOWN`/`PAGE_LEFT`) is implemented from Google's documented `Orientation` enum semantics ("turn the head 90 degrees clockwise... to read" - confirmed via Google Cloud's Document AI reference docs), derived by hand into a rotation-angle mapping, but **not verified against a real rotated fixture** - none of this project's test receipts are actually photographed sideways or upside-down. The fine-tilt correction *is* exercised against real (near-level) photos on every test run, just not at extreme angles, since no fixture has significant tilt either. Both paths are implemented and reasoned through carefully, but carry meaningfully less real-world confidence than the row-clustering and arithmetic-validation logic, which were iterated against live failures on real images.
- `needs_review` rides along in `POST /groups/:groupId/bills/parse-receipt`'s response but has no new frontend UI - `AddBillPage.jsx` already computes its own `subtotalMismatch`/`totalMismatch` banners from the same underlying items/charges/subtotal/total values, so the signal is already visible today through that existing mechanism. Revisit if a use for the flag beyond that (e.g. logging which scans needed a human's attention) comes up.
