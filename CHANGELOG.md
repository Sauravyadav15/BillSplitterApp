# Changelog

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed
- `Navbar`'s wordmark now scales down (icon + text both shrink, `whitespace-nowrap`) instead of hiding on mobile, so "Smart Bill Split" stays visible, clickable, and on one line alongside a correspondingly shrunk Home/Logout button pill down to a 375px-wide screen.
- Added `scrollbar-gutter: stable` to `html` - without it, a `mx-auto`-centered page sits centered within `(viewport width - scrollbar width)` on a page tall enough to scroll, but dead-center in the full viewport on a page that isn't, so the same centered container reads a few pixels off-center depending on which page you're comparing it against (most visible on `GroupPage`, which has enough sections to reliably scroll).
- `AddBillPage`'s crop-step instructions now say specifically what to trim to (start just above the first item, end right after the total; leave out the store header/logo and the footer/payment/loyalty text) instead of the vaguer "trim out the background," with a collapsed-by-default "See an example" disclosure showing a correctly-cropped reference receipt (`frontend/public/crop-example.png`) right above the crop tool.
- Mobile UI cleanup pass: `BillDetailPage`'s mobile item cards were missing `text-sm` on the item name (present on the desktop row version), so it rendered at the page's larger default paragraph size instead - most visible on a long scanned name wrapping to 2-3 lines at an oversized weight. `Navbar`'s "Smart Bill Split" wordmark wrapped onto a second line on phone-width screens (nearly doubling the navbar's height) since nothing shrank or hid it at that width - now icon-only below `sm`, matching the existing pattern for the profile name/avatar. Number inputs (every price/amount field app-wide) no longer show spinner arrows - fiddly to tap precisely on mobile and not useful for entering a price. `type="file"` inputs (`AddBillPage`'s receipt upload) now render a styled button matching `.btn-secondary` via `::file-selector-button` instead of bare unstyled OS chrome. `ReceiptItemCard` (the mobile item-review layout) gained a "Price" label above the price field, matching the existing "Split between" label so the card reads as consistently labeled sections instead of one orphaned unlabeled input.

### Added
- Deployment support for a hybrid hosting split (Vercel frontend + Render backend + Neon Postgres + Cloudinary image storage) — see [ADR 0008](docs/decisions/0008-hybrid-deployment.md). `createBill` now uploads receipt photos to Cloudinary (`utils/cloudinary.js`) instead of keeping them on local disk, which doesn't survive a redeploy on any hosted platform; `parseReceipt`'s scratch OCR-preview upload is unaffected. `frontend/src/api/client.js`'s `API_BASE_URL` is now driven by `VITE_API_BASE_URL` (falls back to `localhost:5000` for local dev), and `resolveImageUrl` passes through an already-absolute (Cloudinary) URL instead of prefixing it. `app.js`'s CORS now honors an optional `CORS_ORIGIN` allow-list, and `config/db.js` auto-enables SSL for any non-localhost `DATABASE_URL` (needed by Neon). Added `render.yaml` (backend Blueprint) and `frontend/vercel.json` (SPA rewrite for React Router) plus `.env.example` in both apps.
- Google Cloud Vision as a selectable OCR backend alongside the self-hosted PaddleOCR worker, switched via `OCR_PROVIDER` (`utils/ocrProvider.js`, `utils/receiptOcrGoogle.js`) — see [ADR 0005](docs/decisions/0005-google-vision-ocr-option.md). Defaults to the existing PaddleOCR path; no change unless `OCR_PROVIDER=google` is set.
- Google Cloud Document AI ("Document OCR" processor) as a third selectable OCR backend (`OCR_PROVIDER=documentai`, `utils/receiptOcrDocumentAI.js`) — see [ADR 0006](docs/decisions/0006-document-ai-ocr-option.md). Document AI's "Expense Parser" processor was evaluated and rejected first: its automatic price/line-item linking was inconsistent on real receipts.
- `utils/receiptParserDocumentAI.js`: a dedicated text parser for the `documentai` OCR provider (switched in by the new `utils/parserProvider.js`, alongside `OCR_PROVIDER`), separate from the shared `utils/receiptParser.js` used by paddle/google. Built around two queues (a pending-name/charge queue and a tentative-price queue) to correctly handle Document AI's line-splitting across several real-receipt failure modes: a per-item code line (e.g. "MRJ") overwriting the real item name, a promo/adjustment line read as a duplicate fake item or replacing a real name outright, a per-unit rate line (e.g. "2 @ $2.69", "$11.00/kg") mistaken for the final price when the real total is a separate later line (including multi-line weighed-item breakdowns), a charge label with no price of its own (e.g. "ECOLOGY FEE") clobbering the real pending item name, and the receipt's real total being misattributed to an unrelated item name once past the SUBTOTAL/TOTAL section. `extractSubtotal`/`extractTotal` now also recover a label's value when it's on the very next line with nothing else on it (previously only same-line "SUBTOTAL 113.65" worked) - safe because it only fires on an unambiguous adjacent pair, unlike a rejected same-work positional heuristic that would've occasionally guessed wrong. Still returns `null` when the label and value are separated by other lines or the label itself is OCR-garbled beyond recognition — see ADR 0006 (also documents one known remaining edge case: a severely OCR-garbled promo line can still close a tentative item price with the wrong intermediate number).
- `bills.purchase_date`: `AddBillPage` now prompts for the date of purchase (defaulting to today) before the rest of the Add Bill form is usable, since a receipt is often scanned days after the purchase itself. Required on `POST /groups/:groupId/bills`, shown on bill cards and the bill detail page in place of `created_at`.
- Additional charges (tax, fees, tip): `receiptParser.js` now recognizes bill-level charge lines (tax, a venue fee like "B.C.H.Fee", a surcharge - see `CHARGE_LABEL_PATTERN`) and pulls them out of the scanned item list into a new `extra_charges` list, instead of letting them get misparsed as purchasable items and inflating the item subtotal. `AddBillPage` shows these in a grey "Additional charges" box after the item list (auto-filled from the scan, editable, with a "+ Add Charge" button for anything OCR missed) alongside `Subtotal` / `Total`, and flags a mismatch against the receipt's own scanned `SUBTOTAL`/`TOTAL` lines (`extractTotal`/`extractTip`). All additional charges split equally across the bill's contributors; a tip is only ever asked about when OCR actually finds one, and can either split equally or be marked as fully covered by one member (excluded from what others owe). See [ADR 0004](docs/decisions/0004-tax-tip-splitting.md) for the split-math design and the new `bills.tip_amount`/`tip_paid_by` columns + `bill_extra_charges`/`bill_charges` tables this required.
- Token-coordinate-based receipt parsing for the `documentai` provider — see [ADR 0007](docs/decisions/0007-token-coordinate-parsing.md). `receiptOcrDocumentAI.js` gained `extractDocumentFromImage`, returning Document AI's full response (per-word pixel geometry, not just text). `receiptParserDocumentAI.js` gained `parseReceiptFromDocument(document)`: reconstructs "lines" directly from each word token's own position (correcting page orientation and estimated skew up to 15°, then clustering tokens into rows by vertical proximity) instead of trusting Document AI's own text linearization — the root cause of most of this file's previously-fixed bugs. Reuses the existing line classifier unchanged on these geometrically-built lines, and only ever trusts the result once it arithmetically reconciles (item prices sum to subtotal; subtotal + charges sum to total) — otherwise falls back to the proven text-based path, unchanged, flagged via a new `needs_review` response field. `billController.js`'s `parseReceipt` feature-detects the new entry points rather than checking `OCR_PROVIDER` directly, so paddle/google are unaffected. Verified against all 14 fixtures: 2 receipts (`bill1.jpeg`, `grocerybill1.jpeg`) recovered data the text-only path could never reach (a name+price pair and a tax charge printed on the same physical row, but split across non-adjacent lines in Document AI's own text order); the other 12 correctly fall back to the already-verified text path with zero behavior change.

### Fixed
- Tests and the dev server shared one database (`DATABASE_URL`) - the test suite's `beforeAll` `TRUNCATE`s every table, so running `npm test` while the app was running wiped every real account, group, and bill. Added `TEST_DATABASE_URL`, a separate database `config/db.js` now switches to whenever `NODE_ENV=test` (which Jest sets automatically), so tests can no longer touch dev data. Requires a new `billsplit_test` (or equivalent) database with `config/schema.sql` applied - see `backend/README.md`.
- `AddBillPage`'s receipt cropper defaulted to a box trimmed 5-10% in from every edge; on a real photo with even a slight tilt, that default was tight enough to clip the first character of left-aligned lines and the last digit of prices, which silently broke `PRICE_AT_END` matching and could drop most or all scanned items. Default crop now starts at the full image instead, so users only trim inward if they choose to.
- `receiptParser.js`'s `PRICE_AT_END` didn't allow a leading `-`, so a receipt line printing a negative price (e.g. a manual return/adjustment line like "FONTAINE SANTE HUMMUS OR DIPS 2  -0.98") was parsed as positive - silently overcharging by 2x the adjustment and leaving a stray `-` on the item name. The sign is now captured as part of the price.
- `receiptParser.js` (PaddleOCR/Vision) didn't recognize "EA" (each) as a unit marker the way it already did `kg`/`lb`, so a "sold by count" item's per-unit-price confirmation line (e.g. "3EA @ $0.99/EA", printed under the item's own already-complete name+price line) was parsed as a second, bogus item named "EA". Added `BARE_EACH_MARKER` to force that line back to the existing "no real name here" fallback instead.
- `receiptParserDocumentAI.js`'s `seenDepartmentHeader` gate (see ADR 0006) never opened at all on receipt formats that print no department header line (e.g. "GROCERY"/"PRODUCE") anywhere on the receipt - confirmed on a real fixture (a Loblaws/Superstore-style bill), where this silently dropped every item and charge on the whole receipt even though OCR text extraction itself was fine. Now pre-scans for whether the receipt has a department header anywhere before deciding whether to gate at all - receipts that do have one behave exactly as before; receipts that structurally never trigger the gate now parse from the first line instead of producing nothing.
- `receiptParserDocumentAI.js` rewritten from a two-queue design to a simpler single-pass state machine (explicit ITEM NAME / ITEM PRICE / ITEM NOTE / DISCARD / FOOTER line classification) - see ADR 0006. Fixes a confirmed real bug where a single stray OCR character (e.g. a bare "H") landing between an item's name and its price would silently overwrite the real pending name and then vanish the item entirely (5 real items lost this way on one fixture); also fixes two-line weight/rate and multi-buy splits (e.g. "0.480 kg" then "$3.28/kg" as separate lines) that were previously misread as a bogus item literally named "0.480 kg" priced at the rate value. Tax/fee charges between SUBTOTAL and TOTAL are now captured positionally (mirroring `extractLabeledAmount`'s existing same-line-or-next-line adjacency rule) instead of only when the label and price were combined on one line - `grocerybill3.webp` previously returned zero charges despite printing a perfectly clean, readable "TOTAL TAX" / "$0.19" pair, simply because charge resolution stopped once past the SUBTOTAL boundary.
- `receiptParserDocumentAI.js`: two further accuracy fixes found while checking the rewrite above against 8 more real receipts. (1) A garbled code fragment fused onto a price line (e.g. "MRJbnpr 5.50", the "MRJ" per-item code plus stray characters) was winning over an already-open pending item name, replacing the real name ("PC DECADENT DARK") with the code fragment - a name now always claims the very next price-bearing line by rule, regardless of what other text also appears on it. (2) A rate/multi-buy line (e.g. "$11.00/kg", "2 @ $2.00") immediately closed the item at the rate value even when a separate, real line total followed right after (e.g. "$11.00/kg" then "11.49") - undercharging by the difference between the per-unit rate and the actual total on every affected item. The price is now held provisional when opened from a rate/multi-buy line, and a following plain value refines it to the real total instead; confirmed correcting several previously wrong-low prices across `grocerybill2.jpg`, `loblawsbill.webp`, `metrobill.jpeg`, `nofrillsBill.webp`, and `longfoodbasicsbill.webp`.
- `receiptParserDocumentAI.js`'s `extractTotal`/`extractSubtotal` gained an arithmetic-verified fallback for when the label-adjacent value is missing or doesn't reconcile with the other (subtotal + charges vs. total) - e.g. Document AI reading "TOTAL" as "ΤΩΤΑΙ" on `loblawsbill.webp`, which `extractLabeledAmount` already correctly refused to guess past, now recovers the real total (`107.75`) by finding a candidate elsewhere in the text whose arithmetic actually checks out, instead of staying null. A candidate is *never* trusted without that check - `extractTotal` searches payment-section markers ("DEBIT", "TENDER", "CAD$", a card network name) and bare values near the end of the receipt; `extractSubtotal` searches from the `SUBTOTAL` label's own position onward (past its adjacent value line, if any) rather than trusting the raw `total - charges` arithmetic on its own, which - caught in testing on two fixtures - could otherwise "verify" itself trivially by rediscovering the very value it started from when no charges were detected (`bill2.jpeg`'s missing tax silently produced a wrong subtotal equal to its total; `grocerybill1.jpeg`'s own subtotal value briefly self-matched as if it were an independent total confirmation). If nothing reconciles, both functions return `null` rather than an unverified guess - including cases where the original unreconciled label-adjacent value is discarded outright (`grocerybill1.jpeg`'s total, `grocerybill2.jpg`'s total) because incomplete charge detection (an undetected tax/fee line) made it impossible to tell whether that value was actually right.
